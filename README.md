# Requirement Alignment · 需求歧义对齐

在 AI 辅助开发前，把未说出口的产品假设变成可以讨论、确认和验收的约定。

## 为什么需要它

用户和 AI 可能对已经谈到的部分达成一致，却对未提及的部分有不同预期。例如，“加一个收藏功能”并没有说明收藏是否跟随账号同步、原内容删除后如何处理，以及本期是否包含分类和分享。这些差异往往到开发后才暴露。

这个 Skill 围绕**当前开发需求**检查隐含假设，集中确认影响最大的分歧，并保存简短的需求约定。目标是减少理解偏差和返工，同时控制用户阅读、回答问题的总负担。

## 如何工作

1. **整理已有信息**：区分明确要求、现有行为、建议默认和待决分歧，避免重复询问已经可查的信息。
2. **找出关键假设**：用具体使用场景检查流程、范围、数据、权限和异常行为。
3. **集中确认**：通常每轮询问 1–3 个高影响问题，提供可理解的选项、后果和推荐。
4. **记录约定**：保存范围、业务规则、采用的默认值和验收场景；未决重大事项仍标为草案。
5. **继续原任务**：关键分歧解决后继续已授权工作；需求变化时只检查受影响的部分。

明确的小改动和已知原因的 Bug 修复通常跳过完整流程。它不追求穷尽全部细节，也不把未回答的问题当成已经确认。

## 使用方式

将本仓库作为一个 Skill 目录安装到工具支持的位置，保留 `SKILL.md`、`references/` 和 `agents/` 的相对结构。具体安装与自动发现方式取决于所用工具；本仓库不宣称所有 AI IDE 都能直接加载。

在支持显式 Skill 调用的 Codex 环境中，可以使用：

```text
$requirement-alignment
我想给现有应用增加收藏功能。先检查我们可能存在的理解分歧，
明确本期范围和关键行为，再按确认后的约定实现。
```

如果只需要梳理需求：

```text
$requirement-alignment
先帮我澄清团队共享收藏的需求，形成约定，暂时不要实现。
```

也可以处理需求变化：

```text
$requirement-alignment
收藏改成只保存在本机。检查这会影响哪些现有约定，
更新相关规则和验收场景。
```

## 一次对齐示例

用户：

> 给应用加一个收藏功能。

AI 在检查项目上下文后，可以集中呈现：

> 我理解本期包括添加、取消和查看收藏，不含分类和分享；建议收藏跟随账号同步。原内容删除后的行为需要决定：A. 收藏一起移除；B. 保留标题并显示失效。我建议 B，避免用户误以为收藏丢失，但需要额外保留标题。你希望采用哪种？如果本期范围有遗漏，也可以直接纠正。

当用户明确接受范围和推荐后，再把规则写入约定。不能仅凭 AI 自己提出建议，就把它记为用户要求。

对应的示例交付物见 [收藏需求约定](examples/favorites-requirements.md)。示例中的选择只服务于演示，不是所有收藏产品的默认规则。

## 输出在哪里

优先更新项目已有需求文档。没有现成文档时，默认保存到：

- 项目内：`docs/requirements/<feature>.md`
- 无项目上下文：当前目录下的 `outputs/<feature>-requirements.md`

用户要求只在对话中处理时，不强制保存文件。

## 当前验证范围

已通过 Skill 格式校验，并检查了规则及示例的一致性。尚未通过真实项目对照验证，因此不承诺减少固定比例的沟通轮数或返工。

评估时建议观察：是否提前发现了真正影响实现的分歧、用户总共需要阅读和回答多少内容，以及开发开始后是否仍需重新决定关键规则。

## 反馈

欢迎通过 Issue 描述：原始需求、未被发现的分歧、期望行为和实际输出。请移除项目密钥、个人信息和其他不宜公开的内容。
